Building High-Throughput CSV Pipelines with Kafka & DLQ Safeguards

Published on June 10, 2026 · 5 min read · 1,200 views

Processing large files (like bulk CSV reports containing millions of items) can easily overwhelm backend servers. Memory leaks, connection timeouts, and database lockouts are typical symptoms of poor architectural boundaries.

At Zenoti, I engineered a highly resilient bulk CSV ingestion pipeline that streams data chunks through Apache Kafka, protecting our core transactional databases. Here is how we designed it.

The Pipeline Architecture

Instead of parsing the entire CSV document in memory and running database operations inside a single HTTP request thread, the pipeline is divided into three distinct stages:

  • Producer Streamer: Validates and reads the uploaded CSV as a stream, emitting structured events to a Kafka topic in micro-batches.
  • Kafka Message Broker: Distributes events across topic partitions to allow parallel consumer horizontal scaling.
  • Consumer Ingestor: Pulls messages, runs business validations, performs deduplication, and performs bulk upserts into PostgreSQL.

Implementing Dead Letter Queue (DLQ) Safeguards

When dealing with a million records, data corruption is inevitable (e.g. malformed strings, null numbers). A single faulty event must not crash the consumer or stall the offset commit. We implemented a Dead Letter Queue (DLQ) pattern. If a message fails parsing or business validations after three retries, it is routed to a secondary DLQ topic for diagnostic analysis.

Below is a simplified C# consumer showing how to catch deserialization errors and route them to a DLQ: 

public async Task ConsumeEventsAsync(CancellationToken cancellationToken)
{
    using var consumer = new ConsumerBuilder<string, string>(_config).Build();
    consumer.Subscribe("lead-uploads-topic");

    while (!cancellationToken.IsCancellationRequested)
    {
        try
        {
            var result = consumer.Consume(cancellationToken);
            var lead = DeserializeOrRouteToDLQ(result.Message.Value, out var error);
            
            if (error != null)
            {
                await _dlqProducer.ProduceAsync("lead-uploads-dlq", new Message<string, string> {
                    Key = result.Message.Key,
                    Value = result.Message.Value
                });
                consumer.Commit(result);
                continue;
            }

            await ProcessLeadRecordAsync(lead);
            consumer.Commit(result);
        }
        catch (ConsumeException ex)
        {
            _logger.LogError($"Kafka consumer error: {ex.Error.Reason}");
        }
    }
}

Results & Key Takeaways

By isolating files into streams and introducing backpressure limits via Kafka's partition offset management, database write locks dropped by 85%, and we processed ~1M records in under 3 minutes with zero memory alerts.
